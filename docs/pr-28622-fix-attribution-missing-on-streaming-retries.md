# Fix missing experiment attribution on streaming retries

Context: During the route experiments beta we saw a subset of streaming requests (SSE) lose experiment attribution after a retry, which caused (a) undercounted per-variant traffic, (b) misleading guardrail charts, and (c) confusing traces where the initial attempt was tagged but the retry attempt was not. This was escalated via SUP-24877 and corroborated by staging attribution-drop dashboards. Root cause: Our streaming retry path reconstructs a new RequestContext / SpanContext for the retry attempt. The base routing decision (including experiment assignment) was persisted on the first attempt, but the retry code path re-evaluated portions of the request pipeline and did not copy experiment dimensions into the retry context. In some cases we also emitted the streaming response headers from the retry attempt before experiment tags were re-attached, so x-redwood-experiment-id / x-redwood-experiment-variant were missing even though the route was in an active experiment. Changes: (1) Persist experiment assignment (experiment_id, variant_id, config_version) into the per-request RetryState and rehydrate it into the retry RequestContext before any OTel spans/metrics are emitted. (2) Ensure the streaming response header writer reads attribution from RequestContext (not transient span tags) so retries remain consistent. (3) Add a guard to prevent re-bucketing on retry unless the original assignment is absent (maintains determinism and prevents variant flipping mid-stream). (4) Add coverage: integration test exercising streaming + injected mid-stream network failure + retry, asserting that experiment dimensions remain stable across attempts and are present on emitted spans/metrics and response debug headers. Safety/rollout: This is behind the existing route experiments feature flag; behavior only changes when retries occur. Added a metric counter for attribution_rehydrated_on_retry to validate impact in canary. Linked work: ADR-048 (attribution schema), PR-28470 (request context plumbing).
Fixes a bug where experiment_id/variant_id attribution could be dropped on server-side streaming retry paths, improving correctness of per-variant metrics and traces in Console.
Logan Wright (Telemetry): The approach makes sense. Can we confirm we’re not increasing cardinality by adding per-attempt tags? Also please ensure we don’t re-bucket on retry; variant flipping would be a nightmare for attribution.
Caleb Johnson (author): Good call. This keeps the same attribution tags per attempt; no new dimensions. Also added a hard guard: if RetryState has assignment, we skip bucketing entirely and just rehydrate. Added assertions in the integration test to prevent variant changes across attempts.
Jordan Lee (Policy Engine): Why not always re-evaluate bucketing for correctness if config changed mid-request?
Caleb Johnson (author): For streaming, we prioritize per-request determinism. Re-bucketing mid-stream can cause headers/metrics mismatch and violate stickiness expectations. If config changes after the first attempt, the next request will pick it up; this keeps a single request consistent.
