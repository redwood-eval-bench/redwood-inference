# Resilient JSON Schema Checkpointing for Tool Calls and Streaming Compatibility Layer

Motivation: Streaming structured output combined with tool/function calls has exposed two classes of failures in production: (1) long-running streams that only produce valid JSON after tool call completions, and (2) brittle clients (including OpenAI-compatible SDKs) that abort on mid-stream invalid fragments. This PR introduces a checkpointing model for JSON schema validation that is tool-call aware, plus an OpenAI-compatible graceful fallback that ensures streaming stability without breaking existing client integrations.

High level: Add a lightweight checkpoint API inside the inference runtime that treats tool-call boundaries and explicit user checkpoints as validation gates. During streaming, the runtime will emit safe partial payloads and maintain an internal checkpointed parse state. When a checkpoint is reached (tool call returned / explicit checkpoint interval), the runtime runs a fast, incremental JSON Schema validation pass against the currently accumulated output. If validation fails at a checkpoint, the runtime will attempt bounded coercion and a single automatic soft-retry (restarts from last successful checkpoint) before emitting a structured-error event to the client. For OpenAI compatibility mode, the runtime can switch to a "raw-stream-fallback" mode that preserves byte-level streaming semantics while annotating the final completion with schema error metadata.

Key behavioral rules implemented: 1) response_format.checkpoint_enabled (default true for structured responses) 2) response_format.checkpoint_interval (configurable char/token boundary heuristic; default 2048 tokens) 3) response_format.strict_validation (boolean; when true, failures at a checkpoint cause a hard reject) 4) toolcall.fence_on_schema (when enabled, tool calls will be buffered until the next successful checkpoint to avoid partial-tool-call side effects) 5) openai_compat.partial_stream_suffix (small metadata suffix appended for compat clients to carry structured-error codes).

Files changed (high level): Added checkpointing controls and validator hooks to runtime/stream_manager.go; incremental validator implementation in runtime/schema_incremental.go; toolcall fencing glue in runtime/tool_fence.go; compatibility shim in compat/openai_stream_fallback.go; unit and integration tests in runtime/tests/checkpointing_test.go and compat/tests/openai_fallback_test.go; docs and config schema in docs/api/response_format.md and schemas/response_format.schema.json. CI: first CI run flagged a flaky test in checkpointing_test.go (race on cached KV state) which was fixed by adding a small mutex and a deterministic test harness; later CI run passes.

Testing & validation: Unit coverage added for incremental validation paths and coercion heuristics. Integration tests simulate mixed streaming with interleaved tool calls and assert no duplicate tool side effects when fencing is enabled. Load tests (benchmarked in perf lab) show a median 3% latency increase under aggressive checkpointing; recommend using adaptive checkpoint_interval for high-throughput customers.

Review notes and decisions: We deliberately keep soft-coercion off by default under response_format.strict_validation to avoid silent output mutation. The default mode for OpenAI compatibility is to prefer raw-stream-fallback rather than hard aborts so third-party SDKs keep working. Toolcall fencing is off by default for backward compatibility; enabling it requires opt-in on per-route config.

Migration & rollout: Feature guarded behind a feature flag; staged rollout to 10% of hosted traffic for two weeks, then 50%, with an opt-in console toggle for Dedicated. A migration page documents how to enable fencing and interpret the new schema error events.
