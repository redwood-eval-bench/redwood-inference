# Add feature flag + cohorting rules for Console onboarding checklist (with kill switch)

Context: We’re rolling out the new onboarding / “first production launch” checklist in Console behind a feature flag, with progressive exposure by cohort. This PR introduces the first-cut flag definition, deterministic cohort assignment, and an emergency kill-switch path that Support/SRE can use if we see regressions during dogfood or cohort rollout. Summary of changes: (1) Adds flag definition `console.onboarding_checklist` with structured config: `enabled`, `mode`, `allowlist_tenants`, `denylist_tenants`, `rollout_percentage`, `cohort_seed`, and `kill_switch` (server-side hard disable). (2) Implements deterministic cohort assignment using stable hashing on `tenant_id` + `cohort_seed` to avoid cohort “flapping” between requests and across regions. (3) Adds a small policy layer to compute exposure in the control plane so Console can request “shouldShowChecklist” with a single API call (rather than duplicating logic client-side). (4) Adds operational guardrails: kill-switch can be toggled via config service and also via `ONBOARDING_CHECKLIST_KILL_SWITCH=1` env var override for emergency response. (5) Adds telemetry events for exposure decisions (aggregated, low-cardinality) to support rollout monitoring: `onboarding_checklist.exposure_evaluated` with fields `{tenant_id_hash, decision, reason, rollout_percentage, mode}`. (Tenant ID is hashed server-side; no org name/email/etc.) Rollout modes: `off` (default), `dogfood` (employee + internal tenants only), `cohort` (percentage-based), `allowlist` (explicit tenants only). Precedence (highest to lowest): kill_switch -> denylist -> allowlist -> mode/percentage. Notes / non-goals: This PR does not include checklist UI (ENG-5814) or progress tracking service changes (ENG-5813). It only provides a consistent mechanism for exposure + safe rollback. Related: PM-768 (Rollout plan and feature flag strategy). Testing: Added unit tests for cohort determinism, precedence ordering, and env-var kill switch. Added integration test to validate consistent exposure decision across regions when config is replicated. Follow-ups: (a) Hook Console UI gating to the new `GET /console/feature-flags` endpoint (tracked in ENG-5814). (b) Add an admin “force enable for tenant” override path for Support (separate PR / ENG-5852).

Dylan Brooks: Can we avoid any client-side cohort math? We’ve had issues where Console and backend diverge and customers see inconsistent UI states across refreshes.
Ethan Park (author): Yep — cohorting is 100% server-side in control plane. Console will call `GET /console/feature-flags` and receive `onboarding_checklist: {enabled: true/false, reason}`. I added reason codes so we can debug “why” without exposing tenant identifiers.
Logan Wright: Telemetry event includes `tenant_id_hash` — can we confirm hashing is stable per tenant but not reversible, and that we’re not emitting raw tenant IDs anywhere?
Ethan Park (author): Good call. Updated to use the existing `hashTenantIdForAnalytics()` helper (salted, non-reversible). Also added a test that fails if raw tenant_id is present in payload serialization.
Aisha Bello: For kill switch, I’d like a path that works even if config propagation is lagging. Env var override is good, but is it wired in all regions and in the right process?
Ethan Park (author): Wired into the control-plane evaluator (the source of truth for the Console endpoint). If we need to hard-disable regionally, we can toggle via deploy-time env var immediately; config kill switch remains the normal path.
Ben Carter: Rollout percentage — are we guaranteed determinism when `rollout_percentage` changes? We should avoid the same tenant bouncing in/out within a day.
Ethan Park (author): Determinism is stable for a given percentage and seed. When percentage increases, only additional tenants get enabled (monotonic). When percentage decreases, some tenants will lose exposure. That’s expected but we should avoid toggling percentages frequently; I added this as a note to the runbook.
Chloe Martin: Precedence looks right. Minor nit: can we rename `mode=dogfood` to make it explicit it’s internal-only? Might be confusing later.
Ethan Park (author): Renamed display string in docs/runbook to “internal_dogfood” but kept wire value as `dogfood` for now to avoid churn across services. Happy to change wire value in a follow-up if we want stricter naming before GA.
