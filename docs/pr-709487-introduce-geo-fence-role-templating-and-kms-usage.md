# Introduce geo-fence role templating and KMS usage metadata tagging with audit tokenization

Add templated RBAC roles scoped to geo-fence claims; attach KMS usage metadata tags for audit correlation; introduce tokenization layer to redact sensitive claim values in audit logs. Backwards compatible: existing role bindings continue to work.
Motivation: Customers operating across multiple jurisdictions need fine-grained operator permissions that automatically adapt to a tenant's geo-claims, without proliferating dozens of static role definitions. At the same time we must ensure KMS usage is attributed with minimal PII in audit logs for compliance teams and regulators. This PR introduces a templating mechanism for RBAC v2 role definitions keyed by geo-claims (geozone, country_code, region_bucket) and a lightweight KMS usage metadata tagging scheme combined with an audit tokenization layer to strip or token-format sensitive claim values before they hit long-term audit storage.

Changes in this PR: 1) Role templating engine: a new role-templater service and a set of YAML templates under internal/rbac/templates/geo-templates/ that allow templates to be expanded into RBAC v2 roles at bind-time. Templates support conditional blocks (e.g., is_eu, is_us_region) and annotation-derived constraints. 2) RBAC admission hook updates: the admission webhook now resolves template placeholders to runtime claims and emits the resolved role fingerprint to a decision cache. This avoids storing cleartext geo-claims in role bindings. 3) KMS usage metadata tagging: when a request uses a customer CMK, the request path now attaches an opaque kms_meta tag (kms_meta.{env,zone_hash,usage_class}) propagated to downstream billing/audit systems. 4) Audit tokenization layer: an extraction and replacement step added to the audit forwarder that replaces raw claim values (email, tenant_geo_id) with reversible tokens (short hash + version) when forwarding to long-term storage while keeping full values in short-lived debugging traces retained in internal logs only. 5) Migration tooling: a small migration that converts a subset of staged role-bindings using the new templating syntax and backfills kms_meta tags for the last 30 days of audit traffic in a best-effort mode.

Testing & CI: unit tests for the templater and admission-hook logic were added (internal/rbac/templater_test.go, internal/webhooks/admission_templater_test.go). End-to-end smoke tests were added to the perf-canary suite to validate token round-trip and KMS tag propagation. The CI pipeline had one flaky integration test (AuditForwarder::deliver_with_retry) that failed once and was retried automatically; the final status is green.

Rollout plan: staged rollout using a feature flag (rbac.geo_templates.enabled) across Dedicated clusters for 2 weeks, monitored by a new observability dashboard (Console -> Security -> Geo RBAC) that tracks template expansion failure rate, decision cache hit rate, and kms_meta propagation. If error rate > 0.1% for 30 minutes we will rollback the flag.

Backwards compatibility: templates do not replace existing static role definitions; if a binding references a static role it is unchanged. The templater will only operate on role-binding files that include the "template:" key.

Migration notes: the included migration script (scripts/migrate_bindings_geo_template.sh) must be run in the operator console with the migration flag enabled and will produce a dry-run report.

Security review: the tokenization design was reviewed by Security (SEC-44) and includes HSM-backed token seeds stored in the key-management service; tokens are reversible only by the audit-token-service which requires a special operator role.

Known limitations: template language does not yet support nested arrays in conditions (to be added in a follow-up), kms_meta currently supports a fixed set of keys; adding new keys requires a small schema bump and downstream mapping updates.

Related work: this PR complements ENG-2081 (decision-cache TTL tuning) and ENG-2130 (audit-forwarder batching improvements).
