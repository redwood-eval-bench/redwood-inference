# Implement KMS failure isolation and immutable audit consensus hash

Motivation: customers with strict data residency and regulated workloads require guarantees that key usage failures or cross-region failovers do not result in silent KMS use outside pinned regions, and that audit logs from disparate replicas can be verified as consistent. This PR introduces two complementary safeguards: (1) a KMS failure isolation and tenant quarantine flow that pins KMS operations to region-aware fallbacks and atomically marks tenant keys as 'quarantined' for operator review when automatic safe failover is not possible, and (2) an immutable audit consensus hash appended to audit batches so downstream validators can assert cross-replica consistency before accepting batched events into long-term retention. The changes are designed to be opt-in per-tenant via RBAC v2 attributes and rolloutable through feature flags.

Design summary and key behaviors: 1) KMS Failure Isolation & Quarantine: - New component services/kms/quarantine_manager.go implements a policy-driven quarantine flow. When primary KMS provider fails for a tenant and no region-bound fallback is available that satisfies the tenant's residency attributes, the system will:   a) fail the in-flight operation with a standard TenantKMSQuarantine error;   b) emit a high-fidelity audit event (quarantine.request) with evidence and suggested operator actions;   c) mark the tenant's KMS profile as quarantined in a new durable store (kvs/tenant_kms_quarantine). Operators can then inspect and either lift quarantine (after manual verification) or approve a controlled fallback. - A new RBAC v2 policy tag rbac.attributes.kms_quarantine_allowed can be used to grant operators or service principals the right to lift quarantine for a tenant. 2) Immutable Audit Consensus Hash: - Each audit batch (per-shard, per-minute) now includes an audit_consensus_hash field that is an HMAC(sha256) over a canonicalized batch payload and a server lattice key. The hash is stored in the audit index and emitted to a new audit-consensus topic. - A verifier utility (tools/audit_consensus_verifier.py) consumes the topic and cross-checks hashes between replicas; discrepancies surface in the Console and trigger an SRE alert and ticket creation flow. - Backpressure semantics: if a shard detects audit hash disagreement across replicas, it will enter a read-only audit-safe-mode for the affected tenant until operator remediation.

Migration and rollout plan: - Feature flag: feature.kms_quarantine.enabled default=false. Gradual rollout per-tenant. - Migration will add the tenant_kms_quarantine table with a compact schema and indexed by tenant_id and region. Migration is non-blocking and can be rolled forward/back without losing audit records. - RBAC: a new role template (roles/kms_quarantine_operator.yaml) is added; Directory/Platform teams must assign it to operator groups for a full rollout.

Testing and verification: - Unit tests for quarantine manager logic and HMAC canonicalization (tests/unit/test_quarantine_manager.py, tests/unit/test_audit_hash.py). - Integration test harness simulates multi-region replica disagreement and verifies Console alerting and safe-mode transition (tests/integration/test_audit_consensus_disagreement.py). - Load tests show <1% CPU overhead for hashing at current batch sizes and negligible latency impact on write path (benchmark/notes/2026-02-kms-quarantine-bench.md).

Operational notes and rollback: - Operators can list quarantined tenants via REST GET /admin/quarantine and clear with POST /admin/quarantine/{tenant_id}/lift if they hold rbac.attributes.kms_quarantine_allowed. - Rollback: disabling the feature flag returns the system to previous behavior; quarantine records remain for audit but are not enforced. - SLO impact: in the rare case of forced quarantine, tenant requests will return 5xx to callers; documented in release notes.

Security considerations: - HMAC key is held in the control plane KMS only; the consensus verifier runs with read-only access to audit topics. - Quarantine store entries include only opaque proofs and no plaintext keys. - RBAC rules were added to restrict who can lift quarantine and to audit all lift operations.
