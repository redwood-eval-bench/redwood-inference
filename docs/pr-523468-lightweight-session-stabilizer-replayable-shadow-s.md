# Lightweight session stabilizer with replayable shadow safeguard

Adds a lightweight session-stabilizer and replayable-shadow safeguard to the rollout controller to improve canary/A-B promotions for sessionful workloads. Motivation: our current staged-promote flow can prematurely promote model variants that break user sessions under slow KV-cache warming and transient routing skew; this PR introduces a non-blocking session quiesce probe, compact session checkpoints (snapshots), and a replayable shadow rehearsal mode that runs a sampled, synthetic replay of live traffic against the candidate model before commit. Key behaviors: (1) stabilizer enforces a minimum session-cohort consistency window during ramp-up to avoid split-affinity anomalies; (2) snapshots are compact (delta encoded) and stored in the rollout ledger so staged rollback can rewind to a known good session mapping; (3) replayable shadow runs on a fraction of traffic with deterministic seeding and preserves ordering to exercise session paths; (4) telemetry gates (latency, user-facing error rate, session-drop metric) are evaluated by the rollout engine and can trigger automatic backout with rewindable snapshots; (5) dry-run mode allows ops to preview snapshot generation and replay without altering routing. Implementation notes: added a new stabilizer plugin (stabilizers/session_stabilizer.go) and a compact snapshot serializer (snapshot/delta_serializer.go); extended the rollout ledger schema with snapshot metadata and retention hints; added a controlled shadow-replay worker pool with deterministic sampling and kv-cache warmup stalls to better surface regressions. Tests and validation: unit tests for snapshot compacting and stabilizer heuristics; integration harness that spins up a mini_shadow_rehearsal job and asserts deterministic replay traces against golden prompts; load-smoke e2e in perf-canary demonstrates no >1% additional p95 token latency overhead when shadow replay is enabled at 5% traffic. Backwards compatibility and rollout safety: the feature is off by default and gated behind rollout policy flags; snapshots use a new namespaced ledger bucket to avoid collisions; we included migration code that will be no-op for customers who do not enable the policy.
