# Record validation artifacts and failure reasons in Fleet Readiness service

Context: Provision-to-ready automation needs actionable failure modes and durable artifacts (logs, summaries) per node before we can safely gate nodes from joining serving pools. Today the orchestrator/agent emits logs, but we lose structured per-step results once a node is recycled, and operators have to grep raw logs to understand why a node is stuck in Validating. This PR adds persistence for validation step results and a structured failure reason field to the Fleet Readiness service, with an API to fetch the latest results for a node and an API-friendly summary intended for internal tooling (ops console/runbooks). Scope: store step name, start/end timestamps, duration_ms, status, failure_reason_code/message, and an artifact pointer (URI + checksum) to bundled logs uploaded by the validation agent. Also adds minimal telemetry for write/read success and payload sizes (no per-node high-cardinality tags). Out of scope: changing the canonical readiness state machine (see ADR-017) or adding UI surfaces; those are in follow-on PRs. Rollout: gated behind a server-side config flag `readiness.persist_validation_results` default OFF; staged enablement planned with SRE after initial data quality checks. Security/PII: artifacts are pointers only; we do not store raw log bodies in Postgres, and artifact URIs are restricted to internal buckets and require service authz to read.
Data model: new table `validation_step_results` keyed by (node_id, attempt_id, step_name) with `status` enum (PASS|FAIL|SKIP|ERROR), `duration_ms` bigint, `started_at`/`finished_at` timestamptz, `failure_reason_code` (short, stable string), `failure_reason_message` (operator-facing, sanitized), `artifact_uri` (s3://... or gs://... depending on env), `artifact_checksum` (sha256), and `artifact_bytes` (int). We also add `last_failure_reason_code/message` and `last_failed_step` denormalized onto `nodes` for fast list queries (used by tooling) and to avoid joining large result sets in summary endpoints. Ingestion: validation agent/orchestrator emits `ValidationStepCompleted` events; the readiness service now upserts step result rows and updates the denormalized last_* fields if the step failed. API: `GET /internal/fleet/nodes/:nodeId/validations?attempt_id=...` returns ordered step results (most recent attempt by default) and includes the denormalized summary. Artifact pointers: the service stores a pointer only; the agent is responsible for uploading a gzipped bundle and providing uri+sha256. We intentionally do not store `artifact_uri` on PASS steps when no logs were uploaded (field nullable).
Unit: schema validation for enums + sanitizer on failure_reason_message. Integration: upsert idempotency (duplicate events), ordering by started_at, and authz coverage for internal read endpoints. Load check: local benchmark verifying ingestion path adds <3ms p95 per step event with Postgres on dev settings. Manual: replayed a real validation agent payload from staging (redacted) and confirmed artifacts show up via API and denormalized summary fields update correctly.

Benji Okafor (author): Agree. Added `sanitizeFailureMessage()` with max length 512 + newline stripping + common secret patterns redaction. Also clarified in docs that full details belong in artifact bundle.
Allison Grant: Please confirm metrics won’t include node_id/pool_id as tags. We already had a cardinality incident risk flagged for this sprint.
Benji Okafor (author): Confirmed. Metrics are only by step_name, status, and region. No node_id, no attempt_id. Added a lint check in telemetry helper to block forbidden tags.
Jordan Lee: Does denormalizing last_failed_step violate ADR-017 (authoritative signals)?
Benji Okafor (author): It’s derived from stored step results, not a separate source of truth. The canonical readiness state still comes from the state machine transitions; this is a query optimization for operator UX.
Aisha Bello: Can we add a histogram for artifact_bytes to catch accidental blowups?
Benji Okafor (author): Added `readiness.validation_artifact_bytes` histogram + alertable dashboard query in follow-up (kept this PR to metrics only; dashboards PR will consume it).
Miles Thornton: What’s the behavior when agent uploads artifact but checksum is missing?
Benji Okafor (author): We reject the artifact pointer (store nulls) and mark the step ERROR with reason code ARTIFACT_METADATA_INVALID. This keeps the node from being marked Ready and gives a clear remediation path.
