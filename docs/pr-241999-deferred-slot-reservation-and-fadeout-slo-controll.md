# Deferred slot reservation and fadeout SLO controller

Problem: short lived overload spikes (bursts of 1-3s) cause immediate tenant eviction when the SLO enforcer aggressively reclaims slots, which produces request loss and oscillating re-admits. Motivation: avoid overreacting to transient bursts while still enforcing SLOs for prolonged overloads. Goal: introduce a short, deterministic reservation window for slots (deferred slot reservation) and a complementary Fadeout SLO Controller that decays allowance over a configurable grace period; provide region-aware coordination so handoffs do not create double-counting and so that failovers remain conservative. Changes: 1) slot manager: add reservation token bucket and reservation lease with TTL; reservation allows a tenant to temporarily exceed strict allocation by N slots for up to T milliseconds; expired reservations are automatically reclaimed. 2) fadeout SLO controller: when a tenant crosses its SLO we no longer instant-evict; instead we move the tenant into a fadeout state where throughput is reduced gradually using a per-tenant penalty curve; the controller integrates with existing penalty decay code and emits explicit audit events for observability. 3) regional synchronizer shim: lightweight lease synchronizer to prevent simultaneous reservation acceptance for the same logical tenant across regions during failover windows. 4) telemetry: new metrics (reservation_attempts_total, reservation_success_total, fadeout_entries_total, fadeout_exit_latency_ms) and dashboards + alert on reservation_rejection_ratio > 5% for 2m. 5) config: feature flag (runtime.feature.deferred_reservations) default off, tuning knobs exposed via console and operator config. Testing & validation: unit and integration tests simulate micro-bursts and long sustained overloads; e2e run in perf-lab with canary traffic showed 48% reduction in immediate evictions and stable latency tail. Rollout: gated canary in 2 regions for 72h, followed by staged rollout with dark traffic validation; automatic kill-switch via feature flag if eviction_delta > 10% or error_rate increases > 0.5%. Backwards compatibility: behavior is opt-in while flag is off; no model/schema changes. Related: ENG-1982 describes production incidents motivating this work; SUP-4421 is a customer incident that required a hotfix for sudden tenant dropouts.
