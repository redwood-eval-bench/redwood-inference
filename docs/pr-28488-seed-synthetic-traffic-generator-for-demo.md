# Seed synthetic traffic generator for demo dashboards (job + presets)

Problem: our demo tenant Console views (usage, latency percentiles, error analysis, cost breakdown) frequently show empty/flat graphs right before a live demo, and the distributions look obviously “fake” when we do a quick manual warm-up. This PR introduces a synthetic traffic generator that continuously produces realistic, policy-driven demo traffic and emits the same telemetry path as real inference (usage + latency + error + trace hooks) so dashboards stay populated and believable. What’s included: (1) a k8s CronJob + ad-hoc runner that hits the demo org’s routes via the public gateway (not direct ingestion) to exercise auth, rate limits, routing, and fallbacks; (2) preset configs (steady, executive-10min, spike, rollout-canary) to cover common demo narratives; (3) a small library for sampling realistic request shapes (prompt length distribution, streaming vs non-streaming mix, tool-calling frequency, structured output schema usage) and injecting controlled error rates (timeouts, 429s, tool validation failures) without overwhelming the tenant; (4) guardrails to ensure this can ONLY target the demo org/project allowlist and cannot run against prod/customer orgs. Motivation: make the demo tenant resilient to “dashboard emptiness” and give SEs a one-command way to warm up the tenant prior to a call, while also generating data that makes cost/latency tradeoffs and reliability/fallback flows visible in the Console. Rollout plan: merge behind DEMO_SYNTH_TRAFFIC_ENABLED, enable in demo env only, then let SRE tune the default schedule/caps after a week of observation.
Traffic is generated via the same public gateway path used by the demo app (so we get auth, quotas, routing, retries, and streaming behavior); requests are labeled with `x-redwood-traffic-source: demo_synth` and scenario tags (scenario=steady|spike|rollout_canary, feature=streaming|tool_calling|structured_output, region=us-east|eu-west). Presets control: QPS target + jitter, streaming ratio, model mix weights, token length distributions, tool-call rate, structured output schema selection, and “controlled failure” knobs. Guardrails: hard allowlist on org_id + project_id, environment check (must be DEMO env), and a max spend cap per hour (tokens + embeddings units) with immediate stop on breach. The CronJob uses a dedicated service account with egress restricted to the gateway; it does not have permissions to call internal admin endpoints.
Unit: distribution sampling (p50/p95 bounds), config parsing, allowlist enforcement; Integration (staging): `rw demo traffic run --preset executive-10min --dry-run=false` against staging demo org, verified dashboards populate within ~2–4 minutes; Load sanity: steady preset capped to avoid triggering 429s (unless explicitly enabled via spike preset).
