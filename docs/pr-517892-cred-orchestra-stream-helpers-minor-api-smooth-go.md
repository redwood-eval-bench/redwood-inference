# Introduce credential-orchestra, stream helpers, and polished retry presets for Go SDK

Motivation: Teams using the Go SDK reported friction composing credential fallback logic with streaming consumers and applying retry presets tuned for low-latency token refresh windows. This PR introduces a small orchestration layer (credential-orchestra) plus a compact set of stream helper utilities and typed retry presets to make common patterns ergonomic and cross-compatible with the polyglot SDKs. Summary of changes: - credential/orchestra: a lightweight coordinator that accepts multiple credential providers (primary, fallback, refresh) and exposes a single Resolve(ctx) API which returns a stable credential handle plus TTL metadata used by stream heartbeats. The orchestra is pluggable and does not change existing provider interfaces. - stream/helpers: utilities to create cancelable, checkpoint-aware stream consumers (PullStreamContext, StreamWithLease) that automatically wire credential refresh signals from the orchestra. Includes a small graceful-resume helper used by long-lived chat sessions. - retry/presets: typed retry profiles (LowLatencyShortWindow, Balanced, Throughput) as Go structs and builder helpers; presets map to backoff/jitter/timeout shapes used by transport-layer calls and stream reconnect logic. - API polish: minor renames to stream factory constructors to reduce ceremony (OpenStream -> NewStream or NewCancelableStream depending on signature); preserved backward-compatible wrappers for older names. - docs and examples: added a new example showing how to compose CredentialOrchestra with a multi-provider configuration and a stream consumer that survives transient auth failures. Implementation notes: - CredentialOrchestra keeps internal lease metadata and exposes events via a simple channel; it never performs network I/O itself, it coordinates provider lifecycles and schedules preemptive refresh callbacks. - Stream helpers subscribe to orchestra events and trigger a soft reconnect when the inside-of-window TTL falls below a threshold; reconnects use the provided typed retry presets to avoid aggressive retries under bursty load. - Retry presets are intentionally conservative by default and overridable; they are annotated so TypeScript/Python teams can mirror the shapes easily in a follow-up. Testing and validation: - Unit tests added for orchestra lifecycle, provider selection ordering, and TTL propagation. - Integration test in the e2e harness that simulates a rotating token endpoint and asserts stream continuity across multiple refresh cycles. - Manual smoke tests with the internal Perf Lab (short chat sessions, high QPS token churn) confirm latency tail improvements when using LowLatencyShortWindow preset. Rollout plan: - This PR is merged into main behind a feature flag (sdk.go.cred_orchestra.enabled=true by default for SDK v1.8.0). - Coordinate with Python/TS SDK maintainers to land counterpart helpers (follow-ups tracked in ENG-2543). - Monitoring: added telemetry hooks to count orchestration-promoted reconnects and measure mean time-to-refresh; dashboards will be created in observability-pack after merge. Known limitations & follow-ups: - CredentialOrchestra currently assumes providers expose TTL metadata; for older providers a shim adapter is required (tracked in SDK-198). - There is a documented follow-up to add an in-memory shared lease cache for multi-process hosters (performance win, tracked in ENG-2627). - TypeScript and Python presets will be added in separate PRs to maintain cross-SDK parity. Backward compatibility: - No breaking changes to public interfaces; renamed constructors have compatibility wrappers that log deprecation warnings for one major release. - Consumers that opted into the new orchestration behavior will see improved stream resilience and slightly different retry timing. Context/related work: mirrors conversations from ENG-2543 and SUP-417 where enterprise customers highlighted token churn when using short-lived delegated credentials in dedicated/private deployments. This PR aims to give SDK users an explicit, observable building block to handle that case without requiring bespoke app logic.
