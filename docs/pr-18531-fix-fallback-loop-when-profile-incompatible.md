# Fix fallback loop in policy evaluation when quantization profile is incompatible

Context: Route-level quantization profiles add a compatibility gate in policy evaluation (model + variant + GPU class + max context + deployment tier). When a profile is explicitly requested but incompatible, we should deterministically fall back to baseline precision once, and emit a clear resolution outcome. Bug: In a rare edge case, policy evaluation could re-enter the quantization resolution step after selecting the fallback target, causing repeated “attempt → incompatible → fallback” loops. This manifested as extra policy eval iterations and, under load, elevated p99 route-resolution latency; in a few cases it amplified registry metadata fetch retries (see SUP-27488). Root cause: The fallback path preserved the original quantization_profile_ref in the intermediate resolved route object and relied on a later normalization pass to clear it. Under certain combinations of (a) tenant override + (b) region policy rewrite + (c) profile alias expansion, the normalization pass didn’t run before the next resolve step, so the resolver kept thinking the request was still requesting the same incompatible profile. Fix: Make fallback terminal within a single evaluation by explicitly setting resolution state to baseline and clearing the profile ref in the resolved policy payload (while still recording the original requested ref in debug/audit fields). Add a loop guard to ensure we only attempt profile application once per evaluation and we don’t re-expand aliases after fallback. Tests: Adds a regression test that constructs the minimal repro: requested profile is incompatible, region rewrite occurs, resolver must return baseline with outcome=fallback_incompatible and attempt_count=1. Also adds a small property-style test over policy rewrite ordering to ensure determinism. Observability: Adds a counter for fallback_loop_prevented (should remain ~0) and tags the decision trace with quant_resolution_stage=terminal when fallback occurs. Notes: No behavior change when feature is off; default route behavior unchanged. This is intentionally conservative for beta/GA safety.
