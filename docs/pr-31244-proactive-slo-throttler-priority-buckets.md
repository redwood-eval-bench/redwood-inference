# proactive-slo-throttler-priority-buckets-and-regional-deg-safety

Motivation: During last month's regional incident we observed that a single noisy tenant could exhaust serving pools and cause SLO violations for unrelated customers. This PR introduces a proactive SLO throttler that enforces soft per-tenant priority buckets and a regional safety controller that applies gentle degradation before hard circuit-breaker tripping. Goals: 1) Reduce tail latency SLO violations by providing deterministic request admission for high-cost requests; 2) Allow low-priority work to be shed early (queueing/soft-deny) while preserving capacity for high-priority traffic; 3) Provide observability hooks and safe rollout with canary and automatic rollback triggers. What this change includes: - A new throttler controller (serving/throttler) that assigns requests to priority buckets using headers + tenant config and exposes admission decisions via a small protocol for front-proxies. - Priority bucket config (config/slo_buckets.yaml) with defaults tuned for common PLG workloads and a per-tenant override API (admin route). - Regional safety controller that monitors regional SLO signals (error_rate, p95 latency, queue_depth) and applies progressive degradation policies: reduce background work allowance -> increase soft-shed rates -> enable degraded model variants. - Metrics and traces: new metrics (throttler.admit_{bucket}, throttler.shed_{bucket}, throttler.decisions_total, slo_safety.trigger_count) and tracing spans so rollout can be audited. - Observability docs and runbook (docs/observability/slo-throttler.md). - Unit + integration tests and a small local perf harness to simulate multi-tenant noisy behavior. Rollout plan: - Canary in us-west-2 with 5% traffic for three days; monitor slo_safety.trigger_count and p95 latency for high-priority buckets. - If canary is stable, increase to 25% and run the perf canary suite. - Automatic rollback if high-priority p95 increases by >10% or error_rate increases by >0.5% for two consecutive 5-minute windows. Backwards-compat: Default behavior is off; can be enabled per-deployment via config flag (serving.enable_slo_throttler). Runtime compatibility: Throttler protocol is backward-compatible — proxies that don't speak to it get a permissive admission policy. Testing: Unit coverage added for admission logic and state transitions; integration test simulates noisy tenant and verifies high-priority success rate stays within configured SLO. Related: ENG-4987 (SLO enforcement epic), ENG-5001 (regional failover safety).
