# Add per-token timing traces and token-level cost/latency dashboard

Motivation: teams building latency-sensitive LLM products need visibility into per-token cost and latency to diagnose model behavior, batching inefficiencies, and tokenizer overhead. This PR adds lightweight per-token tracing spans inside the runtime, surfaces aggregated token latency/cost metrics to Prometheus, adds a new Token Cost & Latency dashboard for the Console, and tunes alert thresholds for token-level SLO breaches. Summary of changes: 1) instrument runtime serving path to emit spans for `tokenize`, `kv_lookup`, `generate_token`, and `response_serialize` with minimal overhead (config guarded); 2) expose histogram metrics: `redwood_token_latency_seconds` (labels: model, route, token_type), `redwood_token_cost_units` (labels: model, route); 3) add a metrics exporter shim to compute token-level cost (cost model is simple CPU/GPU token unit mapping, configurable per-deployment); 4) new Grafana/Console dashboard json for token breakdowns and percentile views; 5) alert tuning: new alert rules for 95/99p token latency regressions and token-cost-per-request increases; 6) docs and release notes. Checklist: - [x] Instrumentation added behind feature flag - [x] Unit tests for metrics emission - [x] Integration test that runs a short generation workload and checks histogram buckets - [x] Dashboard JSON included - [x] Alert rules reviewed with SRE Risk/rollback: instrumentation default-off; deployment will flip feature flag per-cluster. If any metric churn causes noise, revert the flag and roll back dashboard changes. Testing notes: ran local perf canary with 1k short requests and validated p50/p95/p99 token timing stability. See linked Linear tasks for follow-ups (token-label enrichment, cost model tuning). Related: ENG-3245 (token observability epic), ENG-3307 (dashboard work).
