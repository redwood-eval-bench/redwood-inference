# Emit status component tags on API gateway metrics

Motivation: Status page transparency upgrades require us to attribute customer-visible symptoms (errors/latency/stream disconnects) to public components consistently. Today most of our gateway metrics are only tagged by route + model + raw service, which makes it hard to (a) drive component-level dashboards/alerts and (b) generate incident summaries that match the status page taxonomy. This PR adds low-cardinality tags to gateway metrics so the observability-pack and incident tooling can compute component health without guesswork. Scope: (1) Add tags to gateway metrics: component_id, capability, region. (2) Derive these tags from existing request context + the service-to-component mapping (no new external calls on the hot path). (3) Add guardrails to avoid cardinality explosions (no raw path tags; capability is an enum; component_id is from registry; region is from gateway config). (4) Add unit tests + a small integration test that validates tag presence on the key series used by the status classification job. Details: - component_id: computed using the existing internal routing metadata (route_kind + endpoint class) and the mapping table in gateway config; falls back to "unknown" and increments a counter when mapping is missing. - capability: one of {chat, streaming, embeddings, reranking, console, control_plane}; gateway sets streaming when request uses SSE/websocket stream mode (and uses chat otherwise). - region: injected from gateway deployment (REDWOOD_REGION) and normalized to our public labels (us-east, us-west, eu-west, ap-southeast). - Metrics updated: gateway_request_total, gateway_request_errors_total, gateway_request_duration_seconds (histogram), gateway_upstream_latency_seconds, gateway_stream_disconnects_total. Example (Prometheus): gateway_request_errors_total{component_id="hosted-api",capability="chat",region="us-east",status_code="502"} 12 Note: We explicitly do NOT add model_name or route_template as tags here; those remain available via tracing and logs. Follow-ups: After this lands, observability-pack PRs can rely on these tags for component dashboards and the weekly status accuracy audit can attribute incidents correctly. Related: ENG-4830 mapping layer + ENG-4841 component burn alerts. Testing: unit tests for tag derivation; local load test confirmed no material overhead; staging scrape verified series shape and cardinality delta is within budget.
