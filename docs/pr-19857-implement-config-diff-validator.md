# Implement Optimization Config diff + schema/semantic validation with actionable errors

Motivation: As part of Safe Apply + Rollback for Optimization Configs, we need (1) a stable diff between config versions for the Console timeline/diff view and for auditability, and (2) a validation layer that catches schema issues and high-risk semantic issues early with errors that are actually actionable for on-call/operators. This PR adds a generic diff engine for Optimization Config versions (field-level changes with normalized ordering + redaction of sensitive values) and introduces a validation pipeline that runs both JSON schema validation and semantic validation rules. The output format is designed to be consumed by the Console and API clients: each error includes a machine-readable code, JSON pointer path, severity, and remediation text. What’s included: (a) Diff computation: normalized JSON diff with stable ordering, support for arrays where order is not meaningful (e.g., allowlists), and a redaction layer for secret-like fields; diff output includes before/after plus an inferred change_type (add/remove/modify). (b) Schema validation: strict decoding + JSON Schema checks for OptimizationConfig v1; rejects unknown fields by default (with a temporary allowlist for backwards-compat migration fields). (c) Semantic validation rules (non-exhaustive): batching: max_batch_tokens must be <= runtime ceiling, max_concurrent_batches must be > 0, and batching cannot be enabled when scheduler_mode=legacy; caching: prefix_cache.enabled requires kv_cache.enabled and disallows incompatible eviction policies; quantization: quant_profile_id must exist, must be compatible with model_arch, and requires quality_gate_policy when applying outside canary; scoping: region lists must be disjoint across mutually-exclusive scopes; canary: canary_percent must be between 0-50 for production applies unless override flag is set (policy hook stub). (d) Error model: OptimizationConfigValidationError with fields {code, path, message, remediation, severity}; API returns 422 with error list; Console can render inline with highlighted fields. (e) Tests: unit tests for diff stability, golden tests for common error scenarios, and a small set of property tests ensuring diff is symmetric and stable under key reordering. Notes: This PR does not wire into the rollout controller gate evaluation yet; it provides the validation/diff primitives that will be used by apply/rollback endpoints and the Console.
