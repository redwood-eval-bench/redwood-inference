# Introduce schema policy lints, human-readable validation errors, and stream resume tokens for structured output

Context and motivation: Customers increasingly enable response_format/schema on streaming endpoints and then rely on concise error messages to debug integrations. We observed two recurring problems in production: (1) opaque schema validation errors that are hard to map back to a user prompt or tool invocation, and (2) validation failures that surface mid-stream with no way to continue or repair the in-progress stream. This PR introduces three coordinated improvements: a policy linter run at request-compile time, a structured human-readable error format with hint codes, and a stream resume token that allows the runtime to checkpoint validation state across partial payloads.

What this change does: (1) Schema policy lints: adds a new request validation pass that runs when response_format/schema is present. The linter enforces recommended policies (examples present for required top-level objects, disallowing additionalProperties by default unless explicitly allowed, bounding array lengths for large embeddings outputs, and requiring explicit enum lists where applicable). Lints emit warnings (non-blocking) by default and can be promoted to errors with the response_format.strict flag. (2) Human-readable validation errors: validation failures now return an error payload that includes: human_message (concise), hint_code (stable short token), location_path (JSON Pointer), and actionable_suggestion (one-line remediation). These are surfaced consistently across hosted and OpenAI-compat endpoints. (3) Stream resume tokens: when streaming structured output, the runtime emits lightweight resume tokens every time a schema checkpoint is validated. If a later chunk fails, the client (or a server-side repair flow) can provide the last-good token to resume validation without re-processing earlier tokens; this enables graceful repairs and deterministic tool-call fencing.

Compatibility and OpenAI-compat: we preserved the existing response_format and function_call semantics. The OpenAI adapter maps new error hint_codes to openai-compatible error messages, and the adapter will include an x-openai-error-hint header for downstream clients that expect OpenAI-style text. No breaking changes to request shapes when strict is not enabled.

Checklist: - [x] Add policy linter implementation (runtime/request/compiler) - [x] Add structured error schema and serialization layer - [x] Implement resume token generation and verification in streaming runtime - [x] OpenAI-compat adapter mappings and headers - [x] Unit and integration tests for linter + streaming checkpointing - [x] Docs updates (response_format.md and troubleshooting)

Testing and validation performed: - Unit tests (schema linter rules, hint code mapping, resume token deterministic encoding) - E2E smoke against openai-compat harness with simulated partial chunks and mid-stream recovery - Load-tested stream resume in perf-canary (no measurable latency regression at p95) - Manual validation with several customer prompt sets that previously tripped opaque errors

Limitations and follow-ups: - Linter rule set is conservative; we intend to iterate rules and expose a customer-visible policy bundle in a follow-up (ENG-4650). - Resume tokens are intentionally opaque HMACs; we may offer a debug-mode that expands them for internal debugging. - Edge-case: tools that receive partial tool-call bodies still must rely on the tool-call fencing behavior; this PR clarifies behavior but does not change the tool contract.

Notes on rollout: The feature is behind a runtime flag feature.enable_schema_lints and enabled for canary users by default. response_format.strict must be explicitly enabled by customers to convert lints to hard errors.
