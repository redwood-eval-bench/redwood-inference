# Introduce maintenance subnets and safe-route rollout for controlplane provisioning

Background: Private control plane upgrades sometimes require temporary, isolated subnets to perform rolling maintenance, NAT gateway failover, and traffic inspection without affecting live worker subnets. Previously operators created these by hand which led to inconsistent tagging, accidental route overwrite, and outages during maintenance windows. This PR introduces a first-class "maintenance subnet" construct and a safe-route rollout mechanism to automate creation, routing changes, and rollback with preflight checks.\n\nWhat this changes: Adds Terraform and Helm templates to create optional maintenance subnets for each region that host control-plane maintenance tasks. Subnets are tagged deterministically (redwood:role=controlplane-maintenance, redwood:env, redwood:zone) and provisioned with limited egress through a dedicated NAT/inspection path. A new route_rollout module performs staged route updates using an atomic traffic-shift pattern: 1) preflight validation, 2) attach secondary route table to maintenance subnet, 3) shift small percentage of controlplane ENIs, 4) monitor flow logs / health checks, 5) complete shift, 6) optionally rollback on signal or failed health checks.\n\nImplementation notes: - Terraform: module/vpc* updated to accept maintenance_subnet_count, maintenance_tags, maintenance_cidr_prefix. Added route_rollout.tf that uses null_resource + local-exec (aws cli) for staged updates. The rollout implementation is intentionally idempotent and guarded by preflight checks (installer/scripts/preflight-checks.sh). - Helm: controlplane chart gains service endpoint annotations that prefer maintenance subnets for maintenance-only endpoints. - Security: security_groups.tf adds inspection SGs scoped to maintenance subnets; rules are conservative and allow only required controlplane ports and proxy egress to inspection VPC. - Rollback: route_rollout supports an external rollback trigger (S3 flag or Linear web hook). A documented safe rollback routine is included.\n\nTesting and validation: - Unit: new terraform tests under installer/tests validate CIDR allocation, tag invariants, and plan outputs. - Integration (staging): ran rollout in staging with canary 5% traffic shift, monitored flow logs for anomalies, and exercised S3 rollback. - CI: terraform validate + fmt + helm lint run in pipeline; first run failed due to missing module parameter and automatically re-run after fix.\n\nChecklist: - [x] Terraform module added and documented - [x] Helm values and template updates - [x] Preflight script and CI step - [x] Tests (unit/integration) - [x] Release notes entry - [x] Ops runbook updated\n\nRelated: Linear ENG-2149 tracks full automation; SRE-143 requested preflight gating after last outage. SUP-9821 filed a support ticket that motivated opportunistic improvements to tagging and rollback docs.\n\nNotes: This PR avoids modifying existing production subnets or route tables directly; defaults keep maintenance subnets disabled unless maintenance_subnet_count > 0 and rollout enabled. Operators should read installer/docs/controlplane-maintenance.md before enabling in prod.

Adds optional maintenance subnets for control-plane upgrades with a safe route-rollout workflow. Operators must enable maintenance_subnet_count and read the ops runbook before use. Includes preflight checks and documented rollback path.
Before enabling in prod: 1) run installer/scripts/preflight-checks.sh against staging to validate CIDR allocation and IAM perms; 2) ensure inspection VPC endpoints are configured and S3 rollback bucket is accessible; 3) add maintenance_subnet_count in your environment config and perform a staged canary at 5% first.
