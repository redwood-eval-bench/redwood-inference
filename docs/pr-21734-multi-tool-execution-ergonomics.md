# multi-tool-execution: ergonomic API + parallel tool runner + result injection + retry policies

Motivation: Improve ergonomics and reliability for tool/function-calling in the OpenAI-compat layer and native Redwood API. Customers asked for easy multi-tool invocations, deterministic injection of tool results into continuations, safe parallel tool execution, and more robust retry/backoff for transient tool failures. This PR introduces a small, backwards-compatible API extension plus a new parallel tool-runner implementation and runtime wiring for result injection and structured output hints. Summary of changes: 1) API: add `tools` invocation signature that supports multiple tool calls in a single step and an optional `parallel` flag. 2) Runtime: implement ParallelToolRunner with optimistic concurrency, coordinated token streaming, and ordered result injection points. 3) Retry semantics: add configurable retry/backoff policies per-tool with circuit-breaking thresholds and idempotency markers. 4) Structured output: expand function-calling schema to include `injection_point` and `merge_strategy` hints for deterministic consolidation of parallel results. 5) OpenAI compatibility: surface the new multi-tool signature through the OpenAI-compat endpoint with feature gating and compatibility warning headers. 6) SDK: Python and TS client updates for ergonomics and typed helpers. 7) Tests & docs: unit + integration tests for parallel tool execution, backpressure scenarios, and streaming stability; docs and migration guide. Implementation notes and tradeoffs: - Parallel execution is best-effort: by default the runner executes tools concurrently and injects results in the order of `injection_point` when present. If tools have cross-dependencies, callers should use explicit sequential mode or `depends_on` fields. - Streaming: we added a coordinator that merges streaming outputs from active tools into a single response stream while preserving token interleaving semantics. This required a small amount of additional buffering (configurable via runtime flags) to avoid head-of-line blocking. - Retries: only idempotent-marked tools will be automatically retried; non-idempotent tools can opt into safe-retry wrappers. Retries use exponential backoff with jitter and a per-tool max attempt limit. - Backwards compatibility: existing function-calling calls remain unchanged. The new fields are optional and gated behind an SDK flag and an OpenAI-compat header for the next release window. Checklist: - [x] Design doc reviewed by runtime and API teams (ENG-8341) - [x] Prototype validated in perf-canary with small synthetic workload - [x] Unit tests for ParallelToolRunner and retry policies - [x] Integration tests for streaming merge and structured injection - [x] Python + TS SDK helpers + docs snippets - [x] Compatibility guard and migration notes in docs - [x] Load test showing <5% median latency regression on typical chat workloads Known limitations: - Result consolidation for very large tool outputs can increase memory usage; we recommend streaming-friendly tool outputs or chunking. - Deterministic ordering across parallel calls is only guaranteed when callers provide explicit injection points.
