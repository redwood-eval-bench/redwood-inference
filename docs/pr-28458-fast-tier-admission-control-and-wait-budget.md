# Fast-tier tail-latency protections: admission control + strict wait budget + anti-starvation

Context: As part of tiered batching defaults, the fast tier is expected to maintain tight tail latency under mixed workloads and bursty concurrency. Early bench + canary runs showed that continuous batching heuristics that are acceptable for standard/cost-efficient can cause fast-tier p99 regressions when the scheduler accumulates queue depth (especially with mixed prompt lengths and simultaneous streaming + non-streaming traffic). This PR adds fast-tier-specific protections: (1) admission control in overload to keep queue depth bounded, (2) a strict max wait budget (queue time) for prefill admission, and (3) anti-starvation tweaks so long prompts don’t indefinitely block short/older requests when batching is constrained.

What changed: 1) Fast-tier max wait budget: The scheduler now enforces a per-request max_queue_wait_ms when tier=fast. Requests that exceed the wait budget while still queued are dropped early (with a clear reason code) rather than being admitted into an oversized batch that would blow p99. This is implemented at the queue->prefill transition (admission point), using monotonic enqueue timestamps. 2) Fast-tier admission control: When the fast-tier queue is above configured thresholds (queue_depth or estimated_queue_delay), we reject new requests with a retryable overload error (HTTP 429 via gateway mapping; internal status: OVERLOADED_FAST_TIER). This is intentionally stricter than standard tier; goal is predictable degradation rather than slow melting latency. 3) Anti-starvation policy: Fast tier now uses an age-aware selection rule for prefill candidates: prefer older requests within a short window, then apply a short-prompt bias to keep interactive workloads snappy. This reduces cases where the scheduler continuously selects large-prefill requests that maximize throughput but starve small prompts that arrived earlier. The policy is scoped to fast tier only and is gated behind a config flag so we can tune it during canary.

Why this approach: The workload-aware batching project explicitly prioritizes tail latency stability for fast tier. A strict wait budget + overload admission is a common pattern we can explain and monitor. It also provides clean reason codes for debugging (budget exceeded vs rejected at admission) and aligns with the SRE preference: if we can’t meet fast-tier SLO, fail fast with backpressure rather than silently degrading.

Config: Added fast-tier fields under scheduler.tiers.fast: max_queue_wait_ms (default 3ms), admission.max_queue_depth (default 64), admission.max_estimated_queue_delay_ms (default 6ms), starvation.age_bias_window_ms (default 10ms), starvation.short_prompt_tokens_threshold (default 256), and a kill-switch flag scheduler.tiers.fast.enforce_wait_budget. Defaults are set conservatively for the initial rollout; final values will be tuned based on benchmark-lab and perf canary baselines.

Metrics/observability: Added tier-labeled counters and histograms: scheduler_admission_reject_total{tier,reason}, scheduler_wait_budget_exceeded_total{tier}, scheduler_queue_age_ms{tier} (histogram), scheduler_prefill_candidate_age_ms{tier}, and an event in tracing span scheduler.admission with tags tier, admission_decision, and drop_reason. Cardinality controls: reason is a small enum; no route/model labels are added here (those are handled in a separate metrics PR).

Tests: Added unit tests for monotonic queue time accounting and for admission decision boundaries (queue depth/delay). Added a scheduler simulation test covering starvation behavior: mixed request sizes under fixed arrival rates should not allow 90th percentile queue age for small prompts to diverge when fast tier protections are enabled.

Performance notes: On A100-80G, Llama-family 8B chat mix, concurrency ramp 32->256: fast-tier p99 improved ~18–25% in our internal perf harness when bursts occur (at the cost of a small increase in 429s under overload). Under normal load (<= p95 capacity), throughput impact is negligible (<2%). More detail in the benchmark-lab run linked below.

Rollout plan: This PR is meant to land ahead of the tiered defaults feature flag. In canary, we will enable enforce_wait_budget for fast tier on 1% traffic in one region, watch scheduler_wait_budget_exceeded_total and scheduler_admission_reject_total; abort if 429 rate exceeds 0.5% for fast-tier routes at steady state or if p99 does not improve. A follow-up PR will wire these metrics into dashboards/alerts.
