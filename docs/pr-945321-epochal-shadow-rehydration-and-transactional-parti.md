# Epochal shadow rehydration and transactional partial-swap controller

Context: Promoting large sequence models in production can cause transient regression windows when KV caches, attention context, and model warmup are not aligned between shadow and canary lanes. This PR introduces an epochal shadow rehydration subsystem plus a transactional partial-swap controller that reduces blast radius for large model promotes by validating discrete epochs of shadow traffic with replayed state, and only performing cohort swaps when epoch-level invariants hold. Motivation: We need a low-risk path to promote heavyweight models (long context, large KV footprint, quantized variants) while preserving session affinity, deterministic failback, and quick automatic rollback when abundance of regressions are detected. High level changes: 1) new controller: rollout/controller/partial_swap_controller.go implements a 2-phase partial-swap protocol that can atomically move a subset of cohorts once an epoch passes validation gates; it includes commit/prepare semantics and a safety escrow to hold rollback metadata. 2) rehydration engine: rollout/controller/rehydration_engine.go that replays captured shadow traffic into an ephemeral rehydration environment to warm KV caches and validate token-level distributions before promotion. 3) recorder/reader: rollout/recording/* small helpers to chunk and index traffic epochs (epoch IDs are deterministic hashes of window start+policy). 4) simulation harness: rollout/sim/epochal_replayer_test.go that runs synthetic cohort traffic and verifies commit/abort flows under injected latency and partial failures. 5) metrics and alerts: observability/metrics/rollout_rehydrate.metrics registers epoch pass/fail counters, rehydrate latency histograms, and validation regression tags used by playbooks. 6) docs/runbooks/epochal-rehydrate.md runbook describing operator playbook, aborts, and postmortem steps. Checklist: - [x] Design doc attached in Linear (ENG-1229) - [x] Unit tests for controller happy path and rollback - [x] Integration harness for simulated replays (CI-only) - [x] Metrics and dashboards wired - [x] Runbook draft included - [x] Canary smoke on staging passed Summary of behavior: The controller divides shadow traffic into epochs (configurable window, default 5m). For each epoch we: 1) snapshot cohort assignments and record a replay bundle (requests + minimal metadata). 2) spin up an ephemeral rehydration session: warm the runtime with the replay bundle to populate KV caches and trigger kernel selections representative of real load. 3) run validation probes (latency percentiles, reply divergence ratio against golden baseline, and loss/score thresholds). 4) if epoch passes, mark epoch as validated and prepare commit for the cohorts included; once N consecutive epochs (configurable) pass, a transactional partial swap is executed which atomically flips the prepared cohorts to the promoted model while writing a rollback manifest. 5) on failure, cohorts remain on previous model and the system can automatically schedule dry-run rollback or escalate to operator. Safety and rollback: The prepare/commit phases create an escrowed snapshot object (small manifest) that includes input epoch digests, warmed KV checkpoints, and a deterministic revert path. A rollback executor can fast-replay the escrow snapshot to restore prior affinity semantics. Observability and SLOs: New tagging keys enable tracing per-epoch rehydration; dashboards show epoch-level pass rate, median rehydrate latency, and cohort-level divergence. We added alerts: epoch_pass_rate < 85% over 3 intervals triggers auto-quarantine and cancels pending commits. Tests and CI: There was a flaky test in attempt #1 (simulated network partition) which failed the integration job; I fixed a race in the rehydration engine (added a small mutex around ephemeral cache lifecycle) and re-ran CI. Final CI summary below. Migration and rollout plan: This change is behind a feature flag rollout.rollout.experimental.Operators will enable it for a single non-critical customer cohort for 24h, then widen coverage to 10% traffic after success, then 100% with a 2-epoch continuous pass requirement. Backwards compatibility: Existing rollout APIs unchanged; new optional fields added to rollout policies. No immediate breaking change to clients. Related work: builds on earlier shadow replays (ENG-1156) and the partial-snap swap RFC; ties into runtime warmup optimizations (ENG-1194).
Maya Chen: This looks promising — can you explain the decision to require N consecutive epochs? What if traffic is bursty and an intermittent spike causes false negatives?
Arjun Patel (author): Good question — default N=2; idea is to avoid single-epoch flakiness. We also expose epoch window size and require the operator to tune for bursty cohorts. Added a note in README about conservative defaults.
Eloise Kim: We should ensure the escrow manifests are small and don't leak PII. Are we stripping request bodies?
Arjun Patel (author): Escrow bundles contain digests and minimal metadata only (request lengths, hashed tokens). Bodies are not stored. Added unit tests to assert redaction. See rollout/recording/epoch_index.go for scrubber logic.
