# add-sliced-metric-exposures-and-stepped-alert-decimation

Context: we see large volume of noisy SLO alerts that are driven by short-lived micro-spikes in token-phase latencies and tail-cost jitter. Existing alert heuristics operate on coarse per-route percentiles which amplifies noise from low-volume shapes. This PR introduces two orthogonal improvements: (1) Sliced Metric Exposures: a new lightweight metric surface that emits per-route + prompt-shape slices (prompt length bucket, early/late-phase token ratio) for key token-level signals (token_latency_ms, token_cpu_ns, token_cost_microunits) with compact labels to keep cardinality bounded; and (2) Stepped Alert Decimation: an alerting preprocessor that reduces noisy flapping by applying a time-stepped decimation algorithm (shape-aware smoothing + spectral spike suppression) before evaluation by the SLO engine.

Design summary: Sliced exposures are implemented as a thin aggregation layer in observability/metrics that subscribes to the token telemetry stream and emits rollup counters/histograms at three slice dimensions (route, prompt_shape_bin, token_phase). We chose coarse bins to preserve signal while keeping series < 6x existing cardinality. The latency echo matrix dashboard visualizes these slices as a heatmap: x-axis is token phase (init/mid/finish), y-axis is prompt-shape bin, each cell shows median/95/99 latency plus a small sparklines for recent burstiness. The alert decimator lives as an independent pre-eval stage (alerts/step_decimator.py) and exports debug metrics so we can observe how many candidate alerts are decimated vs passed.

Rollout plan: feature-flagged (ff:obs.sliced_exposures) and gated behind a per-tenant sampling opt-in for first 2 weeks. Step 1: enable sliced exposures for internal tenants and run dashboard in read-only mode to validate cardinality and performance. Step 2: enable alert-decimator in passive mode (only record decisions, do not suppress) and run for 72h. Step 3: switch to active decimation for low-volume shapes (<= 10 rps) and monitor alert volume. Step 4: broad enable with gradual increase in shape volume threshold if metrics stable.

Testing and validation: unit tests for decimator logic and e2e integration in tests/alert_decimator_test.go. Load bench for metric emitter to ensure <3% CPU overhead on a busy worker (bench results included in the commit message). Dashboard JSON has been validated with scripts/ci/validate-dashboards.sh. Observability cost impact estimate: ~0.8% ingestion increase for routed tenants, we measured ~2.3% additional disk usage on synthetic replay for internal tenant due to hist granularity; this is acceptable within Dedicated capacity budgets.

Motivation & trade-offs: We intentionally keep slice cardinality coarse to avoid high cardinality explosion. This is not a replacement for per-invocation traces; it is a complementary rollup that lets oncall and the SLO system reason at shape granularity. The decimator uses conservative thresholds by default and is tunable via config in helm/values-observability.yaml.
