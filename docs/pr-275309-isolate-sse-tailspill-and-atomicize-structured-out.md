# Isolate SSE tailspill and atomicize structured-output recovery

Background: In the OpenAI compatibility layer we occasionally observed 'tailspill' where trailing SSE delimiters from one event would bleed into the next fragment, causing consumer-side partial JSON to be misattributed and tool/function call sentinels to reorder. This surfaced as flaky structured-output parses and sporadic function-call ordering regressions under high-throughput muxing. Motivation: users rely on deterministic function call ordering and atomic JSON spans when streaming. This PR isolates delimiter tailspill, enforces an atomic emission policy for JSON-like spans, and introduces a lightweight replay-rescue that recovers truncated JSON without blocking the main stream. Summary of changes: 1) sse: introduce a tail buffer sanitizer that normalizes stray delimiter runs and emits a single canonical separator to downstream consumers; this prevents delimiter amplification across coalesced fragments. 2) parser: add an atomicSpan state that delays emission of structured-output events until the parser confirms a full JSON span (or reaches mapped-timeout/rescue threshold) to avoid exposing mid-json fragments to the function-call dispatcher. 3) adapter: OpenAI-compat adapter now tags fragment epochs so late-arriving bytes can be reconciled into a recovered event rather than treated as a new one. 4) tests: add a deterministic fuzzbed test for interleaved-event ordering and a replay-rescue unit test that simulates partial JSON with delayed bytes. 5) docs: add guidance about the failure-mode and the opt-in rescue_timeout config for customers that prefer lower latency over guaranteed atomicity. Design notes: - The sanitizer is intentionally conservative: it collapses repeating '

' and 'data:' delimiters only when they appear to originate from the same producer epoch; we do not rewrite payload bytes. - atomicSpan is compatible with streaming function-call semantics: when the parser defers emission, function-call sentinels are queued and released in the original logical order once the span is resolved. - Rescue replay is asynchronous and best-effort: if recovery fails by the rescue_timeout, we emit a deterministic error sentinel instead of attempting heuristics that could break downstream JSON consumers. Checklist: - [x] Add sanitizer and parser state - [x] Unit + integration tests - [x] Backwards-compatible adapter changes - [x] Update docs and release notes - [x] Load test with 20K rps muxed stream Observability and migration: New metrics: sse.tailspill_collapses, sse.atomic_span_delays, sse.replay_rescues, sse.rescue_failures. Default behavior preserves prior semantics (rescue_timeout default 250ms). Customers can set rescue_timeout=0 to restore pre-PR low-latency behavior. Compatibility: This is a non-breaking opt-in quality improvement and defaults to safe settings. Risks: slight added latency for streams that frequently produce partial JSON spans; mitigated by config and by collapsing logic which is very cheap. Related: closes ENG-1982, references SUP-4312.
Marcus Klein: Can you explain the epoch tagging strategy? late-arriving bytes could be from reordered TCP segments across proxies.
Author (Anika Sharma): We assign a monotonic epoch per logical producer connection; reconnects reset epoch. The adapter annotates each SSE write with the epoch and sequence id. Late bytes with old epoch are treated as recovery candidates not new events; this avoids cross-connection bleed.
Devon Li: I want to avoid global memory growth if many spans are deferred. What caps do we have?
Author: atomicSpan queue size is bounded per connection (configurable, default 8 spans). When the cap is reached we emit a 'span_overflow' sentinel and fall back to byte-level passthrough to avoid head-of-line blocking.
