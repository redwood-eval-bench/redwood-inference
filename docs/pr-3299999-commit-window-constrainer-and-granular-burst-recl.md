# Commit-window constrainer and granular burst reclaimer

Motivation:\nThis PR introduces a lightweight enforcement layer (CommitWindowConstrain) for per-tenant commit windows and a GranularBurstReclaimer that reclaims unused burst credits more smoothly. The goal is to improve throughput guarantees for Dedicated tenants during sustained load while avoiding hard throttles that cause cascaded latency spikes.\n\nWhat it changes (high level):\n- New controller commit_window_controller: monitors tenant commit windows, underlying pool headroom, and soft-limits per-tenant based on recent usage profiles.\n- GranularBurstReclaimer: returns unused burst credits back to the shared reservoir on a smoothed schedule (exponential decay + jitter) instead of instant forfeiture.\n- New telemetry exports: 99/95/50 utilization percentiles for tenant pools, per-tenant headroom gauge, and a \"reclaim_ramp\" histogram to help correlate reclaim behavior with latency.\n- Configuration surface: a new dedicated section in values.yaml and a runtime config map with knobs: commit_window_ms, reclaim_half_life_s, min_burst_floor, tenant_penalty_backoff.\n- Tests and benchmarks: unit tests for controller logic, integration scenario using the perf-canary harness to validate throughput under synthetic long-tail sequences.\n\nWhy different from previous autoscalers:\nExisting autoscalers optimize fleet size and coarse burst allocation. This work focuses on contract enforcement at the request admission level: rather than immediately blocking tenants that exceed burst expectations, the controller nudges soft-limits and reclaims credits gradually so downstream services see bounded, smooth degradations. It is intended to complement (not replace) existing reservation and warm-pool logic.\n\nChecklist:\n- [x] Implementation of controller + reclaimer\n- [x] Unit tests for core decision functions\n- [x] Telemetry integration and dashboards (draft)\n- [x] Perf scenario validated end-to-end\n- [x] Docs: runbook describing knobs and troubleshooting\n\nRelated: ENG-2345 (throughput-contracts iteration), ENG-2890 (observability for reclamation).\n\nBackwards compatibility and rollout:\nBehavior is gated behind a dedicated feature flag (commit_window_enforce=false by default). Chart / values.yaml ship with conservative defaults (commit_window_ms=2000, reclaim_half_life_s=120). We plan a canary rollout to two pools for 48h with close telemetry watch before enabling by default.\n\nNotes for reviewers:\n- The key heuristic lives in commit_window_controller.go (decision function is documented in comments). We opted for a conservative soft-penalty approach: reduce tenant burst cap by proportional delta and schedule reclaim; after repeated violations tenant_penalty_backoff grows.\n- Reclaimer uses a token-based accounting system; the implementation includes a small deterministic jitter to avoid synchronized spikes across tenants.\n- The telemetry names are intentionally explicit (tenant_headroom_gauge, tenant_util_p95, reclaim_ramp_ms_hist) — reviewer feedback on naming is welcome.\n\nSmall code excerpt (decision logic) for context:\n```\n// if tenant usage over window exceeds commit_window, compute soft reduce\nif observed > config.commit_window_limit {\n  penalty := min(max_penalty, (observed-config.commit_window_limit)/observed)\n  new_cap := current_cap * (1 - penalty)\n  scheduleReclaim(tenant, reclaim_half_life)\n}\n```
