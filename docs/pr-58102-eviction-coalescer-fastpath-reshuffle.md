# eviction-coalescer-fastpath: reduce KV block churn by reshuffle-aware allocator

Motivation: In high-concurrency streaming and sampling workloads we observed excessive KV block churn when multiple small sequences triggered evictions that fragmented the paged block arena. This increases tail latency and the number of block reclaims per token, hurting both latency SLOs and per-token cost. This PR implements a reshuffle-aware allocation fast-path and an eviction coalescer that reduces fragmentation and amortizes writeback/eviction work. Summary of changes: 1) New coalescer layer in the block manager that groups adjacent eviction candidates into a single work unit (src/kv/block_coalescer.rs). 2) Fast-path allocator that attempts a reshuffle (in-place movement) before falling back to full eviction; this avoids unnecessary writeback for hot-vs-warm KB patterns. 3) Scheduler hints to prefer coalescer-friendly allocation windows (src/runtime/scheduler.rs) so that continuous-batching doesn't interleave many small evictions. 4) New metrics and tracing (kv.coalescer.evictions_coalesced, kv.alloc.fastpath_hit_rate, kv.coalescer.work_units) and dashboards updates (docs/perf/kv-cache-metrics.md). 5) A feature flag (kv.ec_coalescer_enabled) gated behind a canary rollout and off by default. Implementation notes: The coalescer uses the existing paged allocator's metadata to identify contiguous-to-logical blocks and collapses them into a single eviction task submitted to the background reclaimer. The fast-path performs a bounded reshuffle (copy within GPU/CPU page) when source and target blocks are colocated and no outstanding readers hold KV snapshots; otherwise it falls back to the safe eviction + writeback path. Care was taken to keep kernel selection stable: allocator fast-path nudges runtime to prefer copy kernels when reshuffle is in-use; no new kernels were added. Testing: unit tests for block_coalescer and fast-path (tests/kv/block_coalescer_unit.rs), integration test that exercises reshuffle under continuous-batching (tests/kv/reshuffle_integration.rs), and new benchmarks (bench/kv/bench_reshuffle.py) that simulate heavy parallel streaming. CI: initial CI run revealed a flaky test (reshuffle race in debug-mode), fixed by adding a lightweight snapshot fence and re-ran checks. Rollout plan: feature flag off by default, enable on canary hosts for 48h and monitor kv.alloc.fastpath_hit_rate, p99 allocation latency, and kv.coalescer.evictions_coalesced. If regressions observed, fallback to old allocator via flag. Related work: builds on prior paged-KV reuse efforts (ENG-7398) and scheduling hints from CONTINUOUS-BATCHING-II (ENG-7223).
