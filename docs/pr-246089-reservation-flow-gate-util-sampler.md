# reservation flow-gate and utilization sampler (per-pool pacing + sampled telemetry)

Background: some Dedicated fleets experience rapid oscillation between reservation allocation and deallocation when a handful of tenants submit bursty traffic with aggressive reservation churn. This causes two problems: (1) churn-driven overcommit and underfill cycles that increase latency tail and cost, and (2) high-cardinality, high-resolution utilization telemetry that floods the metrics pipeline. Goal: introduce a light-weight reservation flow-gate that smooths reservation operations per pool/tenant boundary and a low-cost sampled utilization reporter that emits stable per-pool utilization signals useful for autoscalers and dashboards. This PR implements: 1) ReservationFlowGate controller: a rate-limited admission gate for reservation create/update/delete operations. The gate enforces a token-bucket per-pool pacing policy with configurable burst and refill parameters, plus a short hysteresis window to avoid flip-flopping when utilization hovers near thresholds. 2) SampledUtilizationProxy: an async sampler that aggregates ongoing allocation and throughput measurements and emits probabilistically sampled utilization events (p50/p90 estimates, windowed) to the telemetry bus to reduce cardinality and ingestion cost. 3) Operator flags and defaults: new operator config flags (flow_gate_enabled, pacing_burst, pacing_refill_ms, util_sample_rate) and a sensible default profile for Dedicated fleets. 4) Metrics and dashboards: new metrics exported (redwood_flow_gate_rejected, redwood_flow_gate_allowed, redwood_sampled_util_p50, redwood_sampled_util_p90) and a Grafana dashboard JSON stub for initial observability. 5) Tests and canary: unit tests for gate logic and an integration harness job that runs a mini-canary against the benchmark-lab to validate headroom and tail latency under synthetic churn. Implementation notes: - FlowGate lives in pkg/controller/reservation_flow_gate.go with a small, testable core that accepts an admission decision function for deterministic unit tests. - Sampling is best-effort and non-blocking: it never delays reservation operations. Sampling decisions are independent and bounded to the configured sample_rate to control cardinality. - Backwards compatibility: when flow_gate_enabled is false (default for older clusters), behavior is unchanged; telemetry falls back to existing aggregated signals. Migration & rollout plan: staged rollout as follows: 1) deploy operator with flow_gate_enabled=false and sampling enabled (for telemetry only) to collect baseline signals (2 weeks), 2) enable flow_gate in a single low-traffic Dedicated cluster and run canary scenario (72h), 3) roll to remaining Dedicated clusters with conservative defaults, monitor the new dashboard and set alert: FlowGateRejectionRate > 1% sustained.
