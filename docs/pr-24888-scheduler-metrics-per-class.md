# Scheduler: export per-class queueing + dispatch metrics and trace attrs (short/long)

Context: As part of the mixed-workload scheduler prototype, we need visibility into how the scheduler is behaving per class (short vs long) during benchmarks and canaries, without introducing high-cardinality labels that blow up Prometheus/Grafana. This PR adds per-class metrics and lightweight tracing attributes to the serving runtime scheduler, plus a stub dashboard JSON and metric documentation. Metrics added (all exported from runtime metrics endpoint / Prometheus): 1) Queue depth by class (gauge): redwood_runtime_scheduler_queue_depth{class="short|long"}. 2) Time-in-queue / queue wait time by class (histogram): redwood_runtime_scheduler_queue_wait_seconds_bucket{class="..."} (use PromQL histogram_quantile(0.95, sum(rate(...)) by (le, class)) for p95). 3) Starvation prevention counter by class (counter): redwood_runtime_scheduler_starvation_prevented_total{class="..."} increments when aging forces a long request ahead of short traffic (or equivalent guardrail path). 4) Dispatch share by class (counter): redwood_runtime_scheduler_dispatch_total{class="..."} increments per dispatch decision (note: measures decisions, not tokens; token-level share remains in existing token counters). 5) Prefill latency and scheduler decision time (histograms): redwood_runtime_scheduler_prefill_latency_seconds_bucket{class="..."} and redwood_runtime_scheduler_decision_latency_seconds_bucket{class="..."}. Tracing: Adds OTel span attrs on the existing scheduler/dispatch spans: scheduler.class (short|long), scheduler.queue_wait_ms (integer ms), scheduler.aging_applied (bool), scheduler.token_budget_exhausted (bool). Design/guardrails: - class label is strictly enum {short,long}; NO request_id/model/customer labels are added. - metric names align with Observability naming conventions (prefix redwood_runtime_*, base units in seconds). - histograms use the standard runtime buckets (shared helper) to keep cardinality consistent across SKUs. - starvation counter increments only on the explicit anti-starvation path; it is not a proxy for “badness”, just a signal for tuning. Dashboard: Adds an initial Grafana dashboard stub (not wired to prod folders here) with panels for: queue depth (short vs long), p95 queue wait by class, starvation prevented rate, dispatch share (stacked), and annotations for feature-flag enable. Notes: This PR does not change scheduling policy behavior; it is instrumentation-only and meant to be safe to land before canary enablement. Follow-ups: (1) wire dashboard into the canonical folder + alerts via SRE process, (2) optionally add per-class TTFT breakdown once we decide whether to label TTFT by class or derive it in traces.
