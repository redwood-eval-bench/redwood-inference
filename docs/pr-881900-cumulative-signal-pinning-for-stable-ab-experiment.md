# Cumulative signal pinning for more stable A/B experiments and timed rollback hedging

Context: We see frequent oscillation in short-lived A/B experiments when decisions are driven by high-variance per-cohort metrics (latency/quality) causing noisy promotes/rollbacks and churn in serving capacity. This PR implements a lightweight "cumulative signal pinning" system: cohorts are evaluated against a time-weighted, cumulative metric fingerprint rather than instant window snapshots. The evaluation path produces a pinned cohort decision (promote/hold/rollback) that is stable for a configurable grace period and backed by a compact snapshot used for deterministic rollback and replay. Motivation: Reduce noisy automated rollbacks and reduce thrash on Dedicated pools; preserve fast reaction for true regressions while making borderline signals less likely to flip-flop. Design summary: 1) Metric accumulator: per-cohort accumulator that computes exponential time-weighted aggregates for key signals (p50 latency, error rate, quality delta). 2) Pinning decision: a small state machine that converts accumulated deltas into a pinned state (pinned-promote, pinned-hold, pinned-rollback) with a pin TTL. 3) Snapshot + undo token: when a cohort transitions to pinned-promote we create a compact snapshot (cohort fingerprint) containing model version, routing weights, accumulator summary, and a monotonic epoch id. Snapshots are stored in the rollout journal and can be referenced to perform deterministic rollbacks or to replay traffic for forensic tests. 4) Timed rollback hedging: an optional delay-hedge that postpones automatic rollback for borderline negative signals, while spawning a light-weight shadow replay against cached requests to validate regressions. 5) Console & telemetry: UI shows pinned state, TTL countdown, and a link to the snapshot for quick dump/download. Metrics: added new metrics rollouts.pinning.{state,ttl_seconds,accumulated_delta} and tracing spans around pin transitions. Backwards compatibility: pinning is opt-in via rollout policy; default rollout behavior unchanged. Files changed: controller (core state machine), journal (snapshot store), console (UI indicator), telemetry docs, integration tests, and an e2e scenario for simulated noisy cohorts. Checklist: - [x] Design doc linked (Linear ENG-4421) - [x] Unit tests for accumulator and state transitions - [x] Integration test for snapshot/rollback path - [x] Basic console indicator and snapshot download - [x] Telemetry + dashboards updated - [x] Feature gated behind rollout.policy.pin.enabled and rollout.policy.pin.ttl stages Implementation notes: accumulator uses the existing metrics ingestion pipeline and stores summaries as 128-byte protobufs in the rollout journal to keep runtime memory low. Pin TTL defaults to 5m and can be set per-rollout. During the hedging window the controller spawns a non-blocking shadow replay limited to 1% of traffic routed to a cached buffer to avoid cost blowup. Risk/limits: This reduces sensitivity to short transients but increases time-to-rollback for true, abrupt regressions unless hedging detects them via replay. We validated signal latency with perf-canary profiles to ensure TTL choices don't bypass critical regressions. See comments below for performance numbers. Migration: rollout journal schema version bumped (v7) and an on-start migration writes a format-marker; migration code is idempotent. Related: Linear ENG-4421, ENG-4493 (telemetry dashboards), SUP-871 (customer-reported canary thrash).
