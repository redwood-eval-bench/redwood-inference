# introduce-retry-bundles-and-stream-progress-telemetry-across-sdks

Context: Customers have asked for a compact, declarative way to reuse retry semantics across SDKs and to receive lightweight progress telemetry for long-running streaming requests. This PR introduces (1) retry bundles — named retry/profile presets that can be referenced by "retryPolicy" on client config and (2) a stream-progress telemetry envelope emitted by the SDKs for long-running pull/push streams. Motivation: reduce duplicated retry configuration in apps and enable observability consumers (SLO dashboards, SRE) to surface stream progress without instrumenting app-level callbacks. Summary of changes: added a retry bundle registry and lookup time resolution in the client core; exposed a small opt-in "stream_progress" event channel that SDKs can emit at stable intervals (configurable); implemented consistent semantics across Python/TypeScript/Go; added unit and integration tests and bumped SDK versions. Checklist: - [x] Design doc: linear/ENG-3245 (linked) - [x] Cross-SDK API proposal reviewed by SDK leads - [x] Unit tests for registry lookup and fallback - [x] Integration tests on hosted-compat test harness - [x] Version bumps and changelogs updated - [x] E2E smoke in canary environment (observability) API compatibility: The client constructors accept an optional new field `retry_profile` where callers can pass either a string (bundle name) or an inline profile object. The default remains unchanged unless `retry_profile` is provided. The `stream_progress` channel is opt-in via `enable_stream_progress=true` in client config; when enabled the SDK emits JSON-serializable events that include a monotonic `offset_estimate`, `tokens_emitted`, and `elapsed_ms`. Commits summary: - Add retry-bundle registry, resolution and small DSL for preset values - Wire retry lookup into request pipeline and backoff scheduler - Add stream-progress envelope, interval runner, and config knobs in Py/TS/Go - Add unit tests and integration harness changes - Bump package versions and changelogs Changed files (high level): sdks/python/redwood/client.py, sdks/python/redwood/retry_bundles.py, sdks/python/tests/test_retry_bundles.py, sdks/typescript/src/client.ts, sdks/typescript/src/stream_progress.ts, sdks/typescript/test/retry-bundles.test.ts, sdks/go/client/retry_registry.go, sdks/go/stream/progress.go, docs/sdk/retry-profiles.md Testing notes: - Initial CI run failed lint in TS due to export ordering; fixed in commit 3. - Integration runs on the hosted-canary revealed a timing edge where stream-progress events could be too frequent for very high-throughput streams; added a min-interval clamp and made the interval adaptive. Backwards compatibility and migration: No breaking changes. Existing callers not opting into `retry_profile` or `enable_stream_progress` see no change. Security: retry bundles are client-only; no new server-side surface is exposed. Observability: telemetry envelope follows semantic conventions in docs/sdk/telemetry.md. Related work: touches ENG-3301 (streaming-observability) and SUP-1182 (customer support case requesting standard retry presets).
Add opt-in retry profile bundles and a minimal stream-progress telemetry envelope in Py/TS/Go SDKs. Bump Python to 2.1.0, TypeScript to 1.8.0, Go to v1.6.3. No API surface breaking changes; behavior behind an opt-in flag.
Liam Chen (reviewer): This looks great overall. Two asks: 1) can we document the expected semantics when an inline policy and a bundle name are both provided? 2) TS export ordering caused the lint — please address.
Aisha Kapoor (author): Answered: inline policy takes precedence over bundle lookup; added explicit note in docs and unit test to assert precedence. Fixed TS export ordering in commit d4e5c33.
Priya Natarajan (reviewer): For high-throughput streams, emitting progress every 100ms may be noisy. Can we make the interval adaptive or allow a min-interval?
Aisha Kapoor (author): Implemented adaptive clamp: driver measures tokens/sec and enforces a min interval cap (default 250ms). Added config `min_stream_progress_interval_ms`.
Mateo Alvarez (reviewer): Suggest adding a telemetry tag to help correlate events to requests (trace_id). Is that feasible without plumb changes?
Aisha Kapoor (author): Added optional `trace_context` field to envelope when available; SDKs will attach if a trace id is present in request metadata. No mandatory dependency on tracing libraries.
