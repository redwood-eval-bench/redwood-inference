# Add Security FAQ / RFP snippets to Internal Admin (approved-language library + API)

Summary: This PR adds first-class “Security Snippets” support to Internal Admin so we can centrally manage approved FAQ/RFP text blocks (and their versions) that Sales/SE tooling consumes. This is part of the Enterprise Security Enablement Kit refresh: we’ve had repeated drift between Drive/Confluence snippets, HubSpot templates, and ad-hoc copy/paste. The goal is a single source of truth with clear ownership, review metadata, and safe distribution semantics (no restricted evidence in snippets). Motivation / context: Enterprise security reviews are gating Dedicated/Private deals; field teams need fast, consistent answers without over-claiming. Today, approved language lives across Confluence + Drive and gets copied into various tools. This introduces: (1) a canonical snippet store; (2) an API for downstream consumption; (3) RBAC + audit log events for changes; (4) explicit versioning + “last reviewed” metadata to align with enablement kit governance. Scope (what’s included): - New snippet domain model + persistence: `security_snippets` table (Postgres) with: `key` (stable identifier), `title`, `category`, `deployment_modes` (Hosted/Dedicated/Private flags stored as text), `content_markdown`, `status` (draft|in_review|approved|deprecated), `version`, `last_reviewed_at`, `expires_at` (optional), `owner` (team/alias), `approver` (name), and `notes_internal` (e.g., references to evidence request playbook). - Versioning semantics: update creates a new version row (immutable content by version). “Approved” is per-version; deprecating a version does not delete it. - Internal Admin UI: new “Security & Compliance → Snippets” page with: list + filters (category, status, deployment mode), diff viewer between versions, and an “export” view (raw markdown or plaintext) for downstream tools. - Public/consumption API (internal): `GET /internal/snippets/security?status=approved` and `GET /internal/snippets/security/{key}`. The API returns only non-restricted fields; explicitly excludes `notes_internal` and any future evidence references. - Permissions: gated behind Internal Admin RBAC permission `admin.security_snippets.write` (write) and `admin.security_snippets.read` (read). Default: read for Sales Ops + Solutions Eng; write limited to Security/GRC + Product Security PM. (See reviewers’ notes below re: default grants.) - Audit logging: emits `security.snippet.created`, `security.snippet.updated`, `security.snippet.status_changed` with actor, snippet key, version, and timestamp. These show up in existing audit log pipelines for internal systems. - Seeded initial snippet keys: a small curated set to validate workflow (SSO/SAML, SCIM, RBAC granularity, audit log retention/export, data use/no-training language, encryption in transit/at rest, SOC 2 report request steps). The exact text was copied from the working GTM draft library and then reviewed in this PR; it is not intended to be a complete library in this change. Out of scope / explicit non-goals: - No new product features or promises; no roadmap language. - No restricted compliance evidence (SOC 2 report, pen test reports, vuln scan artifacts) is stored here. Snippets may include the approved process for requesting evidence under NDA, but not the evidence itself. - No direct HubSpot/CRM integration in this PR; the first consumer is the generic response tool (tracked separately) and manual use via export. Implementation details: - Backend: `internal-admin-api` adds `SecuritySnippetService` + repository; migrations in `migrations/2026_02_07_security_snippets.sql`. - Frontend: `internal-admin-ui` adds `SecuritySnippetsPage`, `SnippetEditor` (markdown), and `VersionDiffModal`. - API response includes `content_markdown` and `content_text` (server-side stripped markdown) to reduce divergence between tools that support rich text vs plain text. - All endpoints require admin auth; responses include `etag` and support `If-None-Match` to reduce polling load for downstream tooling. Changed areas (high level): - `services/internal-admin-api/src/security_snippets/*` - `services/internal-admin-api/src/routes/internal/snippets_security.ts` - `services/internal-admin-ui/src/pages/security/SecuritySnippetsPage.tsx` - `packages/rbac/policies/internal-admin.yaml` - `packages/audit-events/src/events/security_snippets.ts` - DB migration and seeds under `services/internal-admin-api/db/*` Example snippet (illustrative, shortened): Key: `sso_saml_scim_overview` Title: “SSO (SAML) + SCIM support” Category: “Access Controls” Content (excerpt): “Redwood supports SAML 2.0 SSO for the Redwood Console and supports SCIM 2.0 for user provisioning with supported IdPs. Role-based access control (RBAC) is enforced for console actions and API keys. For details on supported IdPs and RBAC roles, see the internal capability reference. If a requirement is not currently supported, follow the Security Questionnaire Exceptions Policy.” Test plan: - Unit tests: service + repository (create, new version on update, status transitions) - API tests: auth required; status filter; ETag behavior - UI smoke test: create draft (GRC/Sec role), request review, approve, view diff - Verified audit events appear in internal audit log stream for a status change - Manual: export approved snippets as plaintext and paste into a sample RFP questionnaire section (formatting preserved reasonably) Security / compliance considerations: - RBAC gating prevents broad write access; all mutations are audited. - “No evidence stored” is enforced by process + UI copy: editor includes a warning banner and blocks uploads/attachments. - PII: none expected; we added a lint check in editor that warns (non-blocking) if content appears to include email addresses or phone numbers.
