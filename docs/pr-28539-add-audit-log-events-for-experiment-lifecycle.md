# Audit logging: emit experiment lifecycle events (CRUD/start/stop) with redaction + diff summary

Context: Route-level experiments are now mutable via Console APIs (create/update/start/stop/delete). Enterprise customers and our own compliance posture require an immutable audit trail for configuration changes and lifecycle actions with a predictable schema and safe redaction behavior. This PR adds first-class audit events for experiment lifecycle, wired into the existing AuditLog pipeline, and aligns fields with Security’s requirements doc. Ties to ENG-9030.

What’s in this PR: Adds audit events for the experiment lifecycle actions in the experiment control plane + Console backend APIs: experiment.create, experiment.update, experiment.start, experiment.stop, experiment.delete. Each event includes the required identifiers and a compact change summary while avoiding logging sensitive config fields verbatim. Implements deterministic redaction rules for the experiment spec (especially eligibility rules and any user-provided stickiness key expressions). Adds basic unit/integration coverage to ensure events are emitted exactly once per state transition and never include prohibited fields.

Event schema (high-level): Each audit record contains: event_type (e.g., experiment.update); occurred_at (server time); actor (user/service principal id + type); org_id; project_id (if present); experiment_id; experiment_name; route_ids (normalized ids, not raw paths); environment (hosted/dedicated/private where applicable); request_id; source (console_api | internal_job); result (success | denied | error); error_code (when applicable); config_version_before/config_version_after; and a change_diff_summary (human-readable) plus change_diff_fields (a limited set of keys). NOTE: change_diff_fields is a constrained allowlist to prevent high-cardinality or PII leakage.

Redaction rules: We do NOT log full experiment specs. Specifically redacted/omitted: eligibility rules that may contain user identifiers, header/value matchers, or regexes; any raw stickiness key value observed at request time; prompt content; and customer-provided tags not on the allowlist. For updates, we compute diffs against the persisted canonical spec, then emit (1) a short summary string and (2) the set of changed field paths filtered through an allowlist. Example: we log "allocation.splits changed" and "variant[blue].model_id changed" but not the exact header matcher used in eligibility.

Example payload (illustrative; see AuditLogEvent in code): event_type=experiment.start org_id=org_8f3... actor=user:usr_12... experiment_id=exp_4a... experiment_name="rerank-eu-west-beta" route_ids=["route_7c2", "route_91a"] config_version_before=12 config_version_after=13 change_diff_summary="started experiment; status: DRAFT -> RUNNING; splits unchanged" result=success request_id=req_01HT...

Behavioral details: Emission happens after validation and authorization but before returning success to the caller, and is wrapped so audit pipeline failures do not break the API request (we record a counter + log and continue). For denied attempts, we emit a separate audit event with result=denied and no config diff fields (to avoid leaking existence/structure). For stop/start, the state machine emits from a single transition point to avoid double-emits during retries.

Why now: (1) Beta customers (incl. Helio Finance) asked for audit exports for experiment lifecycle; (2) we need complete audit coverage before GA; (3) support escalations need an authoritative record of who changed what when.

Testing: Unit tests for diff/redaction helper; integration tests for Console mutation endpoints to assert audit events are emitted with expected fields for create/update/start/stop/delete; a regression test ensuring eligibility rules are not present in serialized event payloads. Manual verification in staging via AuditLog viewer + SIEM export pipeline sampling.

Rollout / risk: Low-medium. Primary risk is breaking the audit export schema or causing latency overhead in mutation endpoints. Mitigations: all events use existing async audit publisher; diff computation is O(changed_fields) via canonical struct diff with an allowlist; additional metrics added for publish failures. Feature is guarded behind the existing experiments feature flag for mutation endpoints; audit emission itself is always-on once endpoint is enabled.
