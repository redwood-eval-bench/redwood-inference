# Per-request KMS Selection Hook and Audit Consistency Checker

Adds a per-request KMS selection hook and an audit consistency checker. Backwards compatible, behind feature flag. Improves correct KMS routing for tenant-region constraints and provides stronger audit header validation and canonical audit hash chaining for dedupe and forensic integrity.
Motivation: Customers operating across multiple jurisdictions need deterministic KMS selection per-request so keys and providers respect data residency and tenant-scoped CMK constraints. In parallel, we have recurring incidents where audit headers are inconsistent after gateway routing changes; this makes cross-region deduplication and forensic reconstruction brittle. This PR introduces two coordinated pieces: 1) a per-request KMS selection hook that evaluates tenant claims, requested region, and policy constraints (RBAC v2 attributes) to pick an appropriate key/provider or trigger an approved fallback, and 2) an audit consistency checker that validates incoming audit headers, normalizes provenance fields, and appends a small canonical hash chain (audit-hash) to the audit envelope to enable cross-system dedupe and tamper detection. Design: - Hook is implemented as a pluggable interceptor in the request routing layer (requests/runtime/kms_hook.go) and exposed behind feature flag security.per_request_kms. It consults the policy engine (rbac/v2 policy matcher) with a new attribute set (tenant.cmk_preference, tenant.data_residency, request.region_hint) and returns a KMS selection object (provider, key_id, provenance_token). - Audit consistency checker lives in the audit pipeline (audit/consistency_checker.go). It checks required headers (X-Audit-Tenant, X-Audit-Region, X-Audit-Origin), canonicalizes timestamp/nonce ordering, computes an incremental SHA256-based audit-hash, and writes the resulting metadata to the sealed audit envelope. - Fallbacks: if the hook cannot find a matching key subject to tenant policy, it returns a well-defined error code and optional esk (ephemeral signing key) fallback path that must be authorized by tenant policy (preventing silent cross-region key use). - RBAC v2 integration: a small policy fragment and a new policy template are added so operators can define which service principals can request cross-region key selection. A migration shim keeps existing binary policies until operators roll out the template. - Observability: added metrics (kms_selection.latency, kms_selection.hits_by_policy, audit.checksum_mismatch) and traces. - Tests: unit tests for policy matching, integration tests exercising a simulated multi-kms environment, e2e test that verifies audit envelope chain is preserved across routing and replay. Rollout plan: - Feature gated by security.per_request_kms; opt-in for Dedicated/Private tenants initially. - Canary on a small percentage of hosted traffic with runtime rollout via console. - Monitoring dashboards and alerts added for checksum_mismatch and unexpected fallback usage. Backwards compatibility: existing requests without feature flag behave identical to current code path. The audit checker is non-destructive and only appends audit-hash when all required headers present.
